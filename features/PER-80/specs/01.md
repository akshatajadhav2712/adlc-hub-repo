## Risks

### Risk 1: GraphQL library schema registration mechanism unknown
**Description:** The existing `health()` query's schema registration approach is not visible from the file tree. If the library does not support schema merging or requires a specific registration pattern, extending the schema may be blocked.

**Impact:** High — could block implementation if schema cannot be extended  
**Mitigation:** Investigate `src/health.py` early to identify the GraphQL library (Strawberry, Ariadne, Graphene, etc.) and its schema registration pattern. If merging is not supported, refactor schema registration to a shared entry point before adding todo operations.

---

### Risk 2: Enum serialization format ambiguity
**Description:** GraphQL enum values may serialize as strings (`"DONE"`, `"NOT_DONE"`) or other representations depending on the library's enum handling. The acceptance criteria do not specify the exact response format for the `done` field.

**Impact:** Medium — test failures or client confusion if format does not match expectations  
**Mitigation:** Verify the enum output format in the first integration test (`tests/test_resolvers.py` for AC1). Document the expected response format (e.g., `"done": "NOT_DONE"`) and ensure the Python `TodoStatus` enum maps correctly to GraphQL enum values.

---

### Risk 3: In-memory storage thread safety
**Description:** The module-level `_todos` list is not thread-safe. Concurrent GraphQL requests could cause race conditions (e.g., incomplete writes, lost updates).

**Impact:** Low — acceptable for demo scope per ticket  
**Mitigation:** Document in code comments that the implementation is not production-ready and lacks thread safety. If the service uses async resolvers, ensure mutations complete atomically within a single request. No locking is implemented per the demo scope constraint.

---

### Risk 4: UUID generation predictability in tests
**Description:** UUIDs generated by `uuid.uuid4()` are non-deterministic, which may complicate assertions in unit and integration tests (e.g., verifying the exact `id` value returned by `addTodo`).

**Impact:** Low — tests can work around this  
**Mitigation:** Tests should verify the `id` field is non-empty and consistent across related operations (e.g., the same `id` returned by `addTodo` appears in `todos` query), rather than asserting a specific UUID value. Optionally, use a test helper to capture the returned `id` for subsequent operations.

- **Repo context alignment:** All files are under the `graphql` repository root (`/home/aksj/Documents/adlc-graphql`). No changes to `agent` or `mcp` repositories.
- **Existing health endpoint:** `src/health.py` and `tests/test_health.py` remain completely untouched per AC6.
- **Enum decision:** The `done` field uses a `TodoStatus` enum (`DONE`, `NOT_DONE`) per review feedback (architect_review), not a boolean. This supersedes the original ticket's boolean specification.
- **Storage:** The `_todos` list in `src/todo.py` is initialized as `_todos: list[Todo] = []` at module load and mutated by business logic functions. No persistence layer.
- **Error handling:** Both `add_todo("")` and `complete_todo("nonexistent-id")` raise `ValueError`. The GraphQL resolvers catch these and translate them to user-facing GraphQL errors (not server crashes).
- **ID generation:** Uses Python's `uuid.uuid4()` for simplicity. No external dependencies beyond the standard library.
